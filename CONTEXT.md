## 1. Visão geral

API .NET 10 seguindo **Clean Architecture** (Domain → Application → Infrastructure → Api), construída como template de workshop de pós-graduação FIAP. Expõe endpoints via **Minimal APIs** (não MVC controllers), com versionamento de API, autenticação JWT e autorização baseada em roles.

Solução: `Fiap.Workshop.slnx`

```
src/
  Fiap.Workshop.Domain          # Entidades, Value Objects, eventos de domínio — zero dependências externas
  Fiap.Workshop.Application     # Use cases, boundaries (Input/Output), interfaces (portas)
  Fiap.Workshop.Infrastructure  # EF Core, repositórios, serviços concretos (JWT, hashing, current user, dispatcher)
  Fiap.Workshop.Api             # Minimal API endpoints, DI composition root, validators, mappers HTTP↔Application
tests/
  Fiap.Workshop.UnitTests           # xUnit + Moq/NSubstitute + AutoFixture — Domain e Application isolados
  Fiap.Workshop.IntegrationTests    # xUnit + EF Core real contra SQL Server (docker-compose.tests.yml)
  Fiap.Workshop.FunctionalTests     # xUnit + Microsoft.AspNetCore.Mvc.Testing — projeto criado, SEM testes ainda
```

Regra de dependência: `Domain` não referencia nada; `Application` referencia `Domain`; `Infrastructure` referencia `Application`; `Api` referencia `Infrastructure` (e transitivamente todo o resto).

## 2. Stack e pacotes principais

- **.NET 10** / C# `latest`, `Nullable` habilitado, `TreatWarningsAsErrors=true`, `EnforceCodeStyleInBuild=true` (`Directory.Build.props`)
- **API**: Minimal APIs, `Asp.Versioning.Http` + `Asp.Versioning.Mvc.ApiExplorer` (versionamento via segmento de URL `/api/v{version}/...`; o `ApiExplorer` com `SubstituteApiVersionInUrl = true` é o que faz `{version}` virar `1` de verdade na doc gerada — sem ele, Swagger/OpenAPI mandavam o template cru e todo request pelo Swagger UI dava 404 de roteamento, corrigido em 2026-07-12), `Microsoft.AspNetCore.OpenApi` (gera o documento OpenAPI em `/openapi/v1.json`), `Swashbuckle.AspNetCore.SwaggerUI` (só a UI, em `/swagger` — trocado do Scalar em 2026-07-11, mantendo a geração do doc como estava)
- **Logging**: `Serilog.AspNetCore` (instalado em 2026-07-11) — substitui o provider padrão do `Microsoft.Extensions.Logging` via `builder.Host.UseSerilog(...)` no `Program.cs`; usa bootstrap logger + `try/catch/finally` em volta do host pra capturar falhas de startup (ex.: banco indisponível na migration automática) antes mesmo do DI terminar de montar; sink Console configurado via `appsettings.json` (`Serilog` section, `ReadFrom.Configuration`); `app.UseSerilogRequestLogging()` loga cada requisição HTTP. Todo `ILogger<T>` já injetado nos use cases continua funcionando sem mudança nenhuma — a troca foi só na composição, não no código de Application/Domain.
- **Validação**: FluentValidation (validators na camada Api, um por Request)
- **Auth**: JWT Bearer (`Microsoft.AspNetCore.Authentication.JwtBearer`), policies `AdminOnly`, `AttendantOnly` (roles `Attendant`/`Admin`) e `MechanicOnly` (roles `Mechanic`/`Admin`) — substituíram as antigas `AdminOnly`/`UserOnly` em algum ponto entre 2026-08-08 e 2026-08-11, junto com a mudança de `UserRole` (ver §3): não existe mais um role genérico `User`, só os três papéis de negócio da oficina.
- **Hashing de senha**: `BCrypt.Net-Next` (work factor 12), via `IPasswordService` (`Application.Interfaces.Services`) / `PasswordService` (Infrastructure) — ver §10 para a diferença em relação a uma iteração anterior do projeto que tinha isso como Domain Service
- **Validação de CPF/CNPJ**: pacote `Cpf.Cnpj` (namespace `CpfCnpjLibrary`), usado via `StringExtensions.StandardizeDocument`/`IsValidDocument` (`Application/Commons/StringExtensions.cs`) — ver §4 e §6
- **Persistência**: EF Core 10 + SQL Server (`Microsoft.EntityFrameworkCore.SqlServer`)
- **Testes**: xUnit, FluentAssertions, Moq, NSubstitute (ambos presentes — inconsistência a resolver, ver §9), AutoFixture
- **Erros HTTP**: `AddProblemDetails()` + `UseExceptionHandler()`

## 3. Camada de Domínio (`Fiap.Workshop.Domain`)

> ⚠️ Esta seção foi reescrita em 2026-08-08 para refletir o código real da branch `feature/3-create-user-uc`. Uma iteração anterior do projeto (registrada em commits antigos) havia desenhado `User` com Value Objects (`HashedPassword`, `Email`) e fábricas nomeadas (`Create`/`Rehydrate`); esse desenho **não existe no código atual** — ver nota em §10.

### Abstrações (`Abstractions/`)
- `AggregateRoot` (classe abstrata, **não genérica**): construtor posicional `(Guid id, DateTime createdAt, DateTime updatedAt)`; `Id`/`CreatedAt`/`UpdatedAt` com setter `protected`; lista interna de `IDomainEvent`; `RaiseDomainEvent` (protected), `GetDomainEvents()`, `ClearDomainEvents()`, `SetUpdatedAt()` (protected, `UpdatedAt = DateTime.Now` — trocado de `DateTime.UtcNow` em 2026-08-12 pra manter consistência com o resto do código, que usa `DateTime.Now` em todo lugar, ex. `CreateUserMapper`/`CreateCustomerMapper`). Até `feature/7-get-users`, `SetUpdatedAt()` existia mas **nenhum agregado a usava**; `User` é o primeiro a chamá-la, via `UpdateProfile`/`ChangePassword` (ver abaixo).
- `ValueObject`: igualdade estrutural via `GetEqualityComponents()` — hoje **sem nenhum VO concreto usando** (nenhuma classe do Domain herda dela).
- `DomainException(string message)`: exceção de domínio simples.
- `IDomainEvent`: contrato marcador (não existe `IAggregateRoot` separado).

### Agregado `User` (`Entities/User.cs`)
Propriedades: `Name`, `Password`, `Role` (`UserRole`), `Email` — todas `string`/`enum` simples com setter `private`. **Não há Value Objects.**

Um único construtor **público**, posicional: `User(Guid id, string email, string name, string password, UserRole role, DateTime createdAt, DateTime updatedAt)`. Não existem `Create`/`Rehydrate`/fábricas nomeadas, e não há validação de invariante nenhuma no construtor (nome vazio, formato de e-mail, força de senha — tudo isso, se acontece, acontece na Api, ver §6). O construtor **sempre** dispara `RaiseDomainEvent(new UserCreatedEvent(id))`, inclusive quando `DomainMappers.MapToDomain` (Infrastructure) chama `new User(...)` para reidratar um usuário lido do banco — na prática é inofensivo hoje porque só `UserRepository.AddAsync`/`Update` enfileiram os eventos pendentes no `AppDbContext` (`EnqueueEvents`); leituras (`GetByIdAsync`/`GetByEmailAsync`) descartam o evento junto com o objeto. É um ponto frágil a observar se um dia uma leitura passar a enfileirar eventos — todo `SELECT` de usuário reemitiria "usuário criado".

Dois métodos de comportamento, adicionados em `feature/8-put-users` (2026-08-12) pros use cases `UpdateUser`/`ChangePassword` (ver §4):
- `UpdateProfile(string name, string email, UserRole role)`: muta `Name`/`Email`/`Role` direto e chama `SetUpdatedAt()`.
- `ChangePassword(string newPasswordHash)`: muta `Password` direto e chama `SetUpdatedAt()`.

**Bug corrigido nesta sessão, antes de esses métodos existirem**: a primeira versão de "atualizar usuário" reconstruía um `User` inteiro via `new User(...)` só pra trocar 3 campos — e como o construtor sempre dispara `UserCreatedEvent` (parágrafo acima), isso fazia todo `Update` (mesmo um repeat idempotente) enfileirar um evento de "usuário criado" incorreto via `UserRepository.Update`'s `EnqueueEvents`. `UpdateProfile`/`ChangePassword` resolvem isso na raiz: mutam o agregado já existente em vez de reconstruí-lo, então nenhum dos dois dispara evento. É o padrão a seguir pra qualquer mutação futura de `User` — nunca `new User(...)` pra "atualizar", sempre um método de comportamento dedicado.

### `UserRole` (enum, **mudou entre 2026-08-08 e 2026-08-11**): `Admin = 0`, `Attendant = 1`, `Mechanic = 2`
Substituiu o desenho anterior (`User = 0`, `Admin = 1`) — não existe mais um role genérico `User`; os três valores mapeiam papéis reais da oficina (recepção/atendimento, mecânico, administrador). Todos os testes que fixavam `UserRole.User` foram migrados para `UserRole.Admin` (commit `14b2aac`, "test(refactor): fixing the enum"). Ver policies novas em §2/§6.

### `UserErrors` (constantes de mensagem, hoje **não usadas por nenhum use case** — sobras de uma iteração anterior)
`NameEmpty`, `NotFound`, `EmailAlreadyInUse`, `PasswordEmpty`, `PasswordTooShort`, `PasswordMissingUppercase`, `PasswordMissingLowercase`, `PasswordMissingDigit`, `PasswordHashEmpty`, `InvalidCredentials`.

### Eventos (`Events/`)
- `UserCreatedEvent(Guid UserId)` — disparado (sempre) no construtor de `User`, ver acima. Só carrega o `UserId` ("evento magro"). Ver §11 para a mecânica completa de domain events.

### Agregado `Customer` (`Entities/Customer.cs`) — primeiro agregado de negócio com pilha completa (2026-08-11)
Propriedades: `Name`, `Document`, `Email`, `Phone` — todas `string` simples, setter `private`. **Sem Value Objects, sem validação de invariante no construtor** (nem formato de CPF/CNPJ, nem unicidade) — consistente com a decisão de validação incremental (ver §9/§10): a checagem de formato/dígito verificador de CPF/CNPJ mora na Api (`CreateCustomerRequestValidator`, via `IsValidDocument()`), não no Domain. Construtor único, posicional: `Customer(Guid id, string name, string document, string email, string phone, DateTime createdAt, DateTime updatedAt)`. **Não dispara nenhum domain event** — diferente de `User` (ver §11), `Customer` não tem um `CustomerCreatedEvent` equivalente hoje.

Um método de comportamento, adicionado em `feature/10-update-customer` (2026-08-13) pro use case `UpdateCustomer` (ver §4): `UpdateProfile(string name, string email, string phone)` — muta `Name`/`Email`/`Phone` direto e chama `SetUpdatedAt()`, mesmo padrão do `User.UpdateProfile` (ver acima). **`Document` fica de fora de propósito**: decisão de negócio (não técnica) de que o CPF/CNPJ é imutável depois de cadastrado, igual a um documento de identidade real — não existe (e não é esperado que exista) um jeito de trocar o `Document` de um `Customer` já criado.

### Agregado `Vehicle` (`Entities/Vehicle.cs`) — primeiro agregado com invariante de construtor (2026-08-14, `feature/11-create-vehicle`)
Propriedades: `CustomerId`, `LicensePlate`, `Brand`, `Model`, `ManufactureYear`, `ModelYear`, `Color` — setter `private`. **Primeira entidade do projeto a ganhar validação real no construtor** desde a política de validação incremental (ver §9/§10): `ModelYear` não pode ser anterior a `ManufactureYear` (`VehicleErrors.InvalidModelYear`, lançado como `DomainException`) — decisão consciente de que isso é um fato de negócio sempre verdadeiro (não uma opinião de formatação), então pertence ao agregado, diferente de `User`/`Customer` (zero validação no construtor, tudo na Api). Formato de placa (Mercosul/antigo) **não** é validado aqui — fica na Api (`CreateVehicleRequestValidator`), mesmo racional do CPF/CNPJ em `Customer` (formato de string é responsabilidade da Api; verdade de negócio é responsabilidade do Domain). Por causa dessa mudança, `Vehicle` deixou de usar sintaxe de primary constructor (`class Vehicle(...) : AggregateRoot(...)`) e passou a ter um construtor explícito com corpo, mesmo molde de `ServiceOrderPart`/`ServiceOrderService` (únicas outras entidades que já validavam algo no construtor, mas nunca documentadas aqui em detalhe). **Não dispara domain event**, igual `Customer`.

**Achado crítico corrigido nesta mesma branch**: até então não existia nenhum handler global convertendo `DomainException` em `400` — se uma invariante de domínio estourasse sem tratamento, o cliente recebia `500` genérico do `UseExceptionHandler()` padrão em vez de um erro de negócio `400`. Isso já era um risco latente desde que `ServiceOrderPart`/`ServiceOrderService` ganharam validação no construtor (nenhum use case os instanciava ainda, então nunca tinha sido exercitado). Resolvido com `DomainExceptionHandler : IExceptionHandler` (ver §6) — vale pra `Vehicle` hoje e pra qualquer invariante de domínio futura, sem precisar de `try/catch` local em cada use case.

`Vehicle.UpdateProfile(string brand, string model, string color, int modelYear)` (2026-08-17, `feature/27-vehicle-crud`, ticket 27): revalida `modelYear < ManufactureYear` (mesma checagem/erro do construtor, `VehicleErrors.InvalidModelYear`), muta `Brand`/`Model`/`Color`/`ModelYear`, chama `SetUpdatedAt()` — mesmo molde do `Customer.UpdateProfile`/`User.UpdateProfile`. **`LicensePlate`/`ManufactureYear`/`CustomerId` ficam de fora de propósito** (decisão de escopo do ticket 27, discutida com o usuário antes de implementar — ver §4 pro racional completo e a inconsistência que levantei entre "fato histórico" e "identificador único" como critério de exclusão).

### `VehicleErrors` (`Errors/VehicleErrors.cs`, novo)
`InvalidModelYear` — única constante até agora.

### Agregado `Service` (`Entities/Service.cs`) — segunda entidade do projeto a validar invariante no construtor (2026-08-15, `feature/13-create-service`)
Propriedades: `Code`, `Name`, `Description`, `BasePrice` (`decimal`), `EstimatedDuration` (`short`), `IsActive` (`bool`) — setter `private`. Até esta branch, `Service` usava sintaxe de primary constructor (igual a `Vehicle` antes de `feature/11-create-vehicle`) sem nenhuma validação. **Decisão tomada nesta branch, discutida antes de implementar** (ver `CLAUDE.md` sobre postura crítica em decisões de DDD): as entidades-filhas de `ServiceOrder` no mesmo domínio conceitual de "preço/duração" (`ServiceOrderPart`/`ServiceOrderService`, ver abaixo) já validavam `UnitPrice`/`EstimatedDuration` não-negativos no construtor desde antes — deixar `Service.BasePrice`/`EstimatedDuration` sem a mesma invariante seria uma inconsistência sem justificativa de negócio (preço/duração negativos não são um fato de negócio válido em nenhum dos dois lugares). Por isso `Service` ganhou construtor explícito com corpo, lançando `DomainException` via `ServiceErrors` (`InvalidBasePrice`/`InvalidEstimatedDuration`, ambos "cannot be negative", permitindo `0`) — mesmo molde do `Vehicle` (ver acima), coberto pelo `DomainExceptionHandler` global (ver §6). Formato/obrigatoriedade de `Code`/`Name`/`Description` continuam só na Api (`CreateServiceRequestValidator`), mesmo racional do CPF/CNPJ e da placa. **Não dispara domain event**, igual `Customer`/`Vehicle`.

### `ServiceErrors` (`Errors/ServiceErrors.cs`, novo, `feature/13-create-service`)
`InvalidBasePrice`, `InvalidEstimatedDuration` — únicas constantes até agora, ambas efetivamente referenciadas pelo construtor de `Service` (diferente de `VehicleErrors.InvalidModelYear`, que existe mas está órfão — a mensagem equivalente do `Vehicle` está hardcoded inline no construtor, não referencia a classe; `ServiceErrors` segue o precedente real de `ServiceOrderErrors`, não o de `VehicleErrors`).

**`EstimatedDuration` não tem unidade documentada em lugar nenhum do código** (nem doc comment, nem nome de campo, nem validação) — é só um `short` cru, igual ao `EstimatedDuration` de `ServiceOrderService`. A convenção assumida nos dados de teste (`CreateServiceUseCaseUnitTests`/`IntegrationTests`, valor `60` pra "Oil Change") é **minutos**, mas isso é só uma escolha implícita de quem escreveu o teste, não uma regra imposta em nenhuma camada. **Atualização (`feature/23-complete-service-order`, ticket 23)**: o cenário hipotético que este parágrafo levantava ("comparar com `ActualDuration` real") deixou de ser hipotético — `Service.RecordExecution` (ver abaixo) agora mistura `EstimatedDuration` com o `ActualDuration` informado pelo mecânico na mesma conta aritmética. A unidade continua sem ser formalizada no nome do campo/doc comment (ainda vale o alerta), mas agora as duas pontas (estimativa do catálogo e duração real da OS) já estão de fato acopladas por essa fórmula — uma discrepância de unidade entre elas hoje corromperia a média silenciosamente, não é mais só um risco teórico.

### `Service.ExecutionCount` / `Service.RecordExecution` (2026-08-16, `feature/23-complete-service-order`, ticket 23)

`Service` ganhou `ExecutionCount` (`int`, default `0` — parâmetro opcional no construtor, mesmo padrão do `discount`/`subtotal`/`total` opcionais do `ServiceOrder`, pra não quebrar os call sites existentes de `CreateServiceMapper.MapToDomain`/`DomainMappers.MapToDomain` que não passam esse valor) e `RecordExecution(short actualDuration)`: `EstimatedDuration = EstimatedDuration + (actualDuration - EstimatedDuration) / (ExecutionCount + 1)`, depois `ExecutionCount++`, `SetUpdatedAt()`. **Não valida `actualDuration > 0`** — confia que o chamador (`CompleteServiceOrderUseCase`, ver §4) só invoca com um valor já validado pelo construtor de `ServiceOrderService.RecordActualDuration` (ver abaixo), mesmo racional do `InventoryItem.Reserve` não revalidar `quantity > 0` (ver acima).

**Decisão de design já discutida e fechada com o usuário antes de implementar** (ver `CLAUDE.md`): o desenho original do ticket 23 propunha um relatório calculado separado (tempo médio agregado via `StatusHistory`, por OS). Descartado a favor desta média incremental direto no catálogo — bate melhor com a redação do PDF ("tempo médio de execução **dos serviços**", por tipo de serviço, não por OS) e evita construir infraestrutura de relatório nova. Argumentei contra antes de o usuário decidir: um campo chamado *Estimated* sendo sobrescrito silenciosamente por uma média de execuções reais perde clareza semântica, e é uma mutação de dado de catálogo (mexe em algo que hoje só o `AdminOnly` `CreateService` toca) disparada por um fluxo `MechanicOnly` (`CompleteServiceOrder`). Usuário optou por manter mesmo assim; mitigação: `ExecutionCount` exposto junto no `ServiceResponse` (ver §4), pra quem consome a API saber se o número reflete 1 execução ou 50.

**Achado durante a implementação, sem decisão explícita prévia do usuário sobre a aritmética exata** (só a fórmula já vinha escrita no backlog): como `EstimatedDuration`/`ActualDuration`/`ExecutionCount` são todos tipos inteiros (`short`/`int`), a divisão trunca em direção a zero. Ex.: `EstimatedDuration=60`, `ExecutionCount=2`, `actualDuration=61` → `(61-60)/(2+1) = 1/3 = 0` em aritmética inteira — o valor não se move mesmo com uma amostra real diferente, só `ExecutionCount` avança. Comportamento intencional e coberto por teste dedicado (`ServiceUnitTests`), não um bug corrigido depois — a unidade é minutos inteiros, perder fração de minuto é aceitável; o efeito é só que a convergência da média é mais lenta / enviesada pro valor anterior do que uma média em ponto flutuante seria. Não bloqueou a implementação por não fazer parte do que já tinha sido fechado com o usuário (a fórmula em si, não sua precisão numérica) — registrado aqui como comportamento conhecido.

### `Service.UpdateProfile` (2026-08-17, `feature/28-service-crud`, ticket 28)

`UpdateProfile(string name, string description, decimal basePrice, short estimatedDuration, bool isActive)`: revalida as mesmas duas invariantes do construtor (`BasePrice`/`EstimatedDuration` não-negativos, mesmos `ServiceErrors`), muta `Name`/`Description`/`BasePrice`/`IsActive` direto; **se `estimatedDuration` for diferente do valor atual, também muta `EstimatedDuration` e zera `ExecutionCount`** — decisão já fechada no backlog antes desta branch (ver ticket 28 em `docs/backlog-proximas-tarefas.md`): um `EstimatedDuration` corrigido manualmente pelo admin vira o novo ponto de partida da média incremental, não um valor diluído entre amostras reais antigas e a correção manual. `SetUpdatedAt()` ao final. **`Code` fica de fora**, mesmo racional do `Document`/`LicensePlate` (identificador de catálogo imutável).

**`IsActive` passou a ter um consumidor real nesta branch** — até aqui existia desde a criação (`feature/13-create-service`) mas nenhum código lia o valor. Decisão discutida com o usuário antes de implementar (ver `CLAUDE.md`): deixar `IsActive` editável no `UpdateServiceUseCase` sem nenhuma checagem em nenhum lugar deixaria um "desativar" que não desativa nada de verdade. Fechado junto: `AddBudgetUseCase` (ver §4) agora rejeita um serviço com `IsActive == false` ao montar um orçamento novo.

### Agregado `InventoryItem` (`Entities/InventoryItem.cs`) — terceira entidade do projeto a validar invariante no construtor (2026-08-15, `feature/15-create-inventory-item`)
Propriedades: `Code`, `Name`, `Description`, `QuantityOnHand`/`ReservedQuantity`/`MinimumStock` (`int`), `UnitPrice` (`decimal`), `UnitOfMeasure` (enum), `IsActive` (`bool`) — setter `private`. Mesma decisão tomada em `Service` (ver acima), aplicada de novo por consistência com o precedente agora estabelecido em quatro lugares (`Vehicle`, `Service`, `ServiceOrderPart`, `ServiceOrderService`): `InventoryItem` ganhou construtor explícito com corpo, validando **cinco** invariantes via `DomainException`/`InventoryItemErrors`: `QuantityOnHand`/`ReservedQuantity`/`MinimumStock`/`UnitPrice` não-negativos, mais `ReservedQuantity <= QuantityOnHand` (a regra central do próprio `InventoryItem`, já prevista no backlog pro futuro `Reserve()`/`ReleaseReservation()`/`Commit()` do ticket 20 — "não posso reservar mais do que tenho" — validada aqui como defesa em profundidade mesmo antes de esses métodos existirem, já que `CreateInventoryItem` sempre cria com `ReservedQuantity = 0`). **Não dispara domain event**, igual `Customer`/`Vehicle`/`Service`.

**Efeito colateral em testes existentes**: os testes de `InventoryItem`/mapper que já existiam antes desta branch (`InventoryItemUnitTests`, `InventoryItemMapperUnitTests`) geravam `QuantityOnHand`/`ReservedQuantity`/`MinimumStock` via `_fixture.Create<int>()` independentes — como o gerador de `int` do AutoFixture não garante `ReservedQuantity <= QuantityOnHand`, dois desses testes passaram a falhar assim que a invariante foi adicionada (`DomainException` no construtor). Corrigido trocando pra valores fixos consistentes (`100`/`10`/`5`, mesmo padrão já usado em `InventoryItemRepositoryTests`) — vale lembrar disso se outro agregado ganhar uma invariante cruzando dois campos numéricos gerados via fixture independente.

### `InventoryItemErrors` (`Errors/InventoryItemErrors.cs`, novo, `feature/15-create-inventory-item`)
`InvalidQuantityOnHand`, `InvalidReservedQuantity`, `ReservedQuantityExceedsQuantityOnHand`, `InvalidMinimumStock`, `InvalidUnitPrice`, `InsufficientStock` (novo, `feature/20-add-budget`) — todas referenciadas (as cinco primeiras pelo construtor de `InventoryItem`, `InsufficientStock` por `Reserve(quantity)` abaixo), mesmo precedente real do `ServiceErrors`/`ServiceOrderErrors` (não o de `VehicleErrors`, órfão). `InsufficientStock` é conceitualmente diferente de `ReservedQuantityExceedsQuantityOnHand` (construção/estado válido do agregado vs. uma operação específica não exceder o disponível) — constantes separadas de propósito, como já estava planejado.

### `InventoryItem.Reserve` (2026-08-15, `feature/20-add-budget`, ticket 20)

`Reserve(int quantity)`: lança `DomainException(InventoryItemErrors.InsufficientStock)` se `quantity > QuantityOnHand - ReservedQuantity`, senão incrementa `ReservedQuantity` e chama `SetUpdatedAt()`. Não valida `quantity <= 0` diretamente — confia que o chamador (`AddBudgetUseCase`, ver §4) só invoca com uma quantidade já validada como positiva pelo construtor de `ServiceOrderPart` (`ServiceOrderErrors.InvalidQuantity`), evitando duplicar a mesma invariante em dois agregados.

### `InventoryItem.CommitReservation` (2026-08-16, `feature/21-approve-service-order`, ticket 21)

`CommitReservation(int quantity)`: lança `DomainException(InventoryItemErrors.CommitQuantityExceedsReservedQuantity)` se `quantity > ReservedQuantity`, senão debita **os dois** contadores (`QuantityOnHand -= quantity` e `ReservedQuantity -= quantity`) e chama `SetUpdatedAt()`. É o segundo passo do ciclo de vida de uma reserva de estoque começado por `Reserve` (ver acima): `Reserve` só promete (`ReservedQuantity` sobe, `QuantityOnHand` intocado); `CommitReservation` efetiva a baixa real quando o orçamento é aprovado — chamado por `ApproveServiceOrderUseCase` (ver §4), uma vez por `ServiceOrderPart` da OS.

### `InventoryItem.ReleaseReservation` (2026-08-16, `feature/22-reject-service-order`, ticket 22)

`ReleaseReservation(int quantity)`: lança `DomainException(InventoryItemErrors.ReleaseQuantityExceedsReservedQuantity)` se `quantity > ReservedQuantity`, senão decrementa **só** `ReservedQuantity` (`QuantityOnHand` intocado) e chama `SetUpdatedAt()` — é o terceiro desfecho possível (alternativo ao `CommitReservation`) de uma reserva feita por `Reserve`: se o orçamento é reprovado em vez de aprovado, a promessa de reserva é desfeita sem nunca ter debitado o estoque de verdade. **Decisão discutida antes de implementar** (ver `CLAUDE.md`): o backlog original não previa validação aqui (só "decrementa `ReservedQuantity`"), mas isso deixaria `ReleaseReservation` como a única das três operações de reserva (`Reserve`/`CommitReservation`/`ReleaseReservation`) sem proteção de invariante — usuário confirmou adicionar a mesma checagem por consistência, mesmo sem um caminho de chamada conhecido hoje que a violaria (o único chamador, `RejectServiceOrderUseCase`, sempre passa quantities vindas de `ServiceOrderPart`s já reservados pelo próprio `AddBudget`). Chamado por `RejectServiceOrderUseCase` (ver §4), uma vez por `ServiceOrderPart` da OS.

### `ServiceOrderService.RecordActualDuration` (2026-08-16, `feature/23-complete-service-order`, ticket 23)

`ServiceOrderService` ganhou `ActualDuration` (`short?`, `null` até a OS ser concluída — parâmetro opcional trailing no construtor, mesmo mecanismo do `Service.ExecutionCount` acima, pra `DomainMappers.MapToDomain` conseguir reidratar o valor persistido sem quebrar os outros call sites que não o informam) e `RecordActualDuration(short actualDuration)`: valida `actualDuration > 0` (`DomainException(ServiceOrderErrors.InvalidActualDuration)`, mensagem própria — não reaproveita `InvalidEstimatedDuration`, que teria o nome de campo errado na mensagem), seta `ActualDuration`, `UpdatedAt = DateTime.Now` (sem `SetUpdatedAt()` — `ServiceOrderService` não é `AggregateRoot`, é entidade-filha de `ServiceOrder`, mesmo molde do resto da classe). Chamado por `ServiceOrder.Complete` (ver abaixo), uma vez por `ServiceOrderService` já persistido na OS.

### Agregado `ServiceOrder` (`Entities/ServiceOrder.cs`) — primeiro use case exposto em `feature/17-create-service-order` (2026-08-15)
Propriedades: `CustomerId`, `VehicleId`, `CreatedBy`, `Status` (`ServiceOrderStatus`, default `Received`), `ProblemDescription`, `DiagnoseDescription` (opcional), `OdometerReading`, `Discount`/`Subtotal`/`Total` (default `0`), `OpenedAt`, `ClosedAt` (opcional) — setter `private`. Ainda usa sintaxe de primary constructor com parâmetros opcionais (`status`/`diagnoseDescription`/`discount`/`subtotal`/`total`/`closedAt` todos com default), **sem nenhuma validação de invariante no construtor** — diferente de `Vehicle`/`Service`/`InventoryItem`, mas consistente com a política incremental (ver §9/§10): as invariantes reais de `ServiceOrder` (transição de status válida, desconto dentro do subtotal) só fazem sentido quando os métodos que as violam existirem (`StartDiagnosis`/`AddBudget`/`Approve`/etc., tickets 19-24, ainda não implementados) — `ServiceOrderErrors` já tem as mensagens prontas (`InvalidStatusTransition`, `InvalidDiscount`, `OrderClosed`) esperando por eles. Tem três coleções de filhos do mesmo agregado (`Parts`/`Services`/`StatusHistory`, cada um com seu próprio `Errors/ServiceOrderErrors.cs` compartilhado), todas vazias na criação (`AddParts`/`AddServices`/`AddStatusHistory` existem mas `CreateServiceOrder` não os chama — "OS nasce sem orçamento", decisão já fechada no backlog). `ServiceOrderPart`/`ServiceOrderService` já validam `Quantity`/`UnitPrice`/`EstimatedDuration` no construtor desde antes desta branch (únicas entidades com essa validação antes de `Vehicle`/`Service`/`InventoryItem`, ver notas acima). **Não dispara domain event**, igual `Customer`/`Vehicle`/`Service`/`InventoryItem`.

**Decisão discutida e revertida nesta branch, antes de implementar** (ver `CLAUDE.md` sobre postura crítica): o backlog original (`docs/backlog-proximas-tarefas.md`, ticket 17) previa um campo `Number` (int sequencial, tipo "OS #1042") gerado por `SEQUENCE`/`IDENTITY` no SQL Server. Investigado e descartado — **`ServiceOrder` **removeu** o campo `Number`, usa só `Id` (Guid) como identificador**. Dois motivos:
1. Qualquer forma de gerar um `Number` sequencial de verdade (sem gaps, coordenado entre múltiplas instâncias da API) exige uma autoridade central — só o banco serve esse papel aqui (não há Redis/coordenador distribuído no projeto). Gerar um "sequencial" só em C# teria condição de corrida entre instâncias concorrentes.
2. A forma mais simples de fazer o banco gerar esse valor (coluna `IDENTITY`/`DEFAULT NEXT VALUE FOR ...`) colide com o padrão que **todo** use case de criação já segue neste projeto: construir a entidade em memória → persistir → devolver o DTO montado a partir dessa **mesma instância em memória**, sem reler do banco depois do commit (`CreateVehicle`/`CreateService`/`CreateInventoryItem`, ver §4). Um `Number` gerado pelo banco só existiria de fato na linha persistida, não no objeto em memória usado para montar a resposta — exigiria inventar um mecanismo de releitura pós-commit só para este campo.
3. A alternativa que preservaria o `Number` sem quebrar o padrão (buscar o próximo valor de uma `SEQUENCE` via um método de repositório **antes** de construir o agregado — mesma categoria de chamada que `GetByIdAsync`/`ExistsWithCodeAsync` já fazem hoje) foi levantada e rejeitada pelo usuário por ainda envolver uma consulta ao banco só para obter o número.

Decisão final: sem esse identificador curto/humano-legível, `Id` (Guid) já cobre unicidade — a referência "OS 1042" não é um requisito confirmado do negócio. Se um dia isso importar (impressão de ordem de serviço, atendimento por telefone), reabrir a discussão com a opção 3 acima como caminho mais consistente com o resto do projeto.

`ServiceOrderPart`/`ServiceOrderService`/`ServiceOrderStatusHistory` deixaram de ser filhos permanentemente vazios do agregado nesta e na branch anterior (ver `AddBudget`/`StartDiagnosis` abaixo).

### `ServiceOrder.StartDiagnosis` — primeiro método de transição de status (2026-08-15, `feature/19-start-diagnosis`, ticket 19)

`StartDiagnosis(string diagnoseDescription, Guid changedBy)`: valida `Status == ServiceOrderStatus.Received` (senão `DomainException(string.Format(ServiceOrderErrors.InvalidStatusTransition, Status, ServiceOrderStatus.Diagnosing))`), seta `DiagnoseDescription`, muda `Status` para `Diagnosing`, chama `SetUpdatedAt()` — mesmo molde de `User.UpdateProfile`/`Vehicle`/`Service` (validação de invariante lançando `DomainException`, capturada pelo `DomainExceptionHandler` global, ver §6).

**Decisão tomada durante a implementação, antes de codar** (ver `CLAUDE.md` sobre postura crítica): o backlog original (ticket 19) previa só `StartDiagnosis(string diagnoseDescription)`, sem tocar em `StatusHistory`. Like `Parts`/`Services`, `StatusHistory` já é modelado no agregado e já é exposto pelo `GetServiceOrder` desde `feature/18` — mas nenhum ticket do backlog (19 a 24) previa populá-lo. Deixar como estava faria `StatusHistory` ficar permanentemente vazio em produção: infraestrutura modelada e exposta, nunca escrita. Discutido com o usuário, que optou por já estabelecer o padrão nesta primeira transição em vez de repetir a lacuna nos próximos cinco use cases (tickets 20-24, todos vão seguir o mesmo molde: capturar `Status` anterior, mudar `Status`, adicionar um `ServiceOrderStatusHistory(Guid.NewGuid(), Id, previousStatus, Status, changedBy, DateTime.Now)` via `_statusHistory.Add(...)`). `changedBy` (quem fez a transição) passou a ser parâmetro do método — vem de `ICurrentUserService` na Api, não do corpo da requisição, mesmo racional do `CreatedBy` em `CreateServiceOrder`.

**Achado de infra durante a implementação**: adicionar um filho novo (`ServiceOrderStatusHistory`) a uma `ServiceOrder` já persistida expôs de imediato o bug já diagnosticado no §5 (o mesmo que já bloqueava o ticket 20) — corrigido nesta branch, mas só para `StatusHistory`. **Estendido para `Parts`/`Services` em `feature/20-add-budget`** (ver §5) — o gap está totalmente fechado agora.

### `ServiceOrder.AddBudget` — segundo método de transição de status (2026-08-15, `feature/20-add-budget`, ticket 20)

`AddBudget(IEnumerable<ServiceOrderService> services, IEnumerable<ServiceOrderPart> parts, Guid changedBy)`: valida `Status == ServiceOrderStatus.Diagnosing` (senão `DomainException(InvalidStatusTransition)`, mesmo molde do `StartDiagnosis`), calcula `Subtotal = Σ(UnitPrice × Quantity)` de todos os serviços e peças recebidos, adiciona os filhos via `AddServices`/`AddParts` (reaproveitados, não duplica a lógica de `_services.AddRange`/`_parts.AddRange`), seta `Subtotal`/`Total = Subtotal` (**sem `Discount`** — ver decisão abaixo), muda `Status` para `AwaitingApproval`, registra a transição em `StatusHistory` (mesmo padrão do `StartDiagnosis`) e chama `SetUpdatedAt()`.

`ServiceOrderPart`/`ServiceOrderService` que entram aqui já vêm "fotografados" do catálogo (`Name`/`Description`/`UnitPrice` copiados de `InventoryItem`/`Service` no momento da criação, não uma referência viva) — é o `AddBudgetUseCase` (ver §4) quem monta esses objetos antes de chamar `AddBudget`, não o método do agregado; a instanciação em si foi extraída pro `Mapper/AddBudgetMapper.cs` da Application (ver §4), não fica inline no use case.

**Decisão revista pelo usuário logo após a primeira versão desta branch**: `AddBudget` originalmente recebia `decimal discount` e já validava `0 <= discount <= Subtotal` (`ServiceOrderErrors.InvalidDiscount`), setando `Total = Subtotal - Discount` ali mesmo. Removido — "montar o orçamento" (quais peças/serviços entram, quanto custam) e "aplicar um desconto" são decisões de negócio distintas, com potencial de ator/timing diferentes (o backlog fechado hoje não especifica quem/quando aplica desconto), e misturar as duas no mesmo método acoplava algo que ainda não foi desenhado. `Discount` permanece no agregado (propriedade já existe desde `CreateServiceOrder`, sempre `0` por padrão) e `Total = Subtotal` enquanto nenhum desconto for aplicado. `ServiceOrderErrors.InvalidDiscount` volta a ficar órfã (sem consumidor) — igual estava antes desta branch — esperando por um futuro use case de desconto, ainda não modelado nem no backlog (nenhum dos tickets 21-24 cobre isso). Não inventar esse desenho agora; só registrar o gap.

### `ServiceOrder.Approve` — terceiro método de transição de status (2026-08-16, `feature/21-approve-service-order`, ticket 21)

`Approve(Guid changedBy)`: valida `Status == ServiceOrderStatus.AwaitingApproval` (senão `DomainException(InvalidStatusTransition)`, mesmo molde do `StartDiagnosis`/`AddBudget`), muda `Status` para `InProgress`, registra a transição em `StatusHistory`, chama `SetUpdatedAt()` — mais simples que `AddBudget`, não toca em `Parts`/`Services`/`Subtotal`/`Total` (o orçamento já foi fechado, `Approve` só registra a decisão do atendente/cliente e libera a execução). Quem debita o estoque de verdade (`InventoryItem.CommitReservation`, ver acima) é o `ApproveServiceOrderUseCase` (ver §4) — mesmo racional do `AddBudget`/`Reserve`: `ServiceOrder` não mexe em `InventoryItem` diretamente (agregados diferentes), a orquestração fica na Application.

### `ServiceOrder.Reject` — quarto método de transição de status (2026-08-16, `feature/22-reject-service-order`, ticket 22)

`Reject(Guid changedBy)`: valida `Status == ServiceOrderStatus.AwaitingApproval` (senão `DomainException(InvalidStatusTransition)`, mesmo molde do `Approve`), muda `Status` para `Cancelled`, registra a transição em `StatusHistory`, chama `SetUpdatedAt()` — estrutura idêntica ao `Approve` (mesma pré-condição de status, o caminho "aprovar" e "reprovar" partem do mesmo estado `AwaitingApproval`), só o status de destino muda. Quem libera a reserva de estoque de verdade (`InventoryItem.ReleaseReservation`, ver acima) é o `RejectServiceOrderUseCase` (ver §4), mesmo racional do `Approve`/`CommitReservation`.

### `ServiceOrder.Complete` — quinto método de transição de status (2026-08-16, `feature/23-complete-service-order`, ticket 23)

`Complete(IReadOnlyCollection<(Guid ServiceOrderServiceId, short ActualDuration)> durations, Guid changedBy)`: valida `Status == ServiceOrderStatus.InProgress` (senão `DomainException(InvalidStatusTransition)`, mesmo molde das outras transições); compara o conjunto de ids de `_services` com o conjunto de ids em `durations` via `HashSet.SetEquals` — se não bater exatamente (falta um `ServiceOrderService` da OS, ou sobra uma entrada que não corresponde a nenhum), `DomainException(ServiceOrderErrors.MissingServiceDuration)`; chama `RecordActualDuration` (ver acima) em cada `ServiceOrderService` já existente na coleção (não adiciona filhos novos — diferente do `AddBudget`, aqui só muta os que já foram persistidos); muda `Status` para `Completed`; registra em `StatusHistory`; `SetUpdatedAt()`. **Assinatura usa tupla nomeada** (`(Guid ServiceOrderServiceId, short ActualDuration)`) em vez de um tipo dedicado — único método do projeto a fazer isso na API pública do Domain; aceito porque o backlog já especificava essa assinatura concreta (decisão tratada como fechada, não uma escolha nova desta branch) e o par id+duração não carrega nenhuma regra própria que justificasse um Value Object.

`ServiceOrder` não mexe em `Service` diretamente (agregados diferentes, mesma fronteira já respeitada por `AddBudget`/`InventoryItem` — ver acima) — quem atualiza a média incremental do catálogo (`Service.RecordExecution`, ver acima) é o `CompleteServiceOrderUseCase` (ver §4), depois que `Complete` já populou `ActualDuration` em cada `ServiceOrderService`.

### `ServiceOrder.Deliver` — sexto e último método de transição de status (2026-08-16, `feature/23-complete-service-order`, ticket 24, implementado fora de sequência)

`Deliver(Guid changedBy)`: valida `Status == ServiceOrderStatus.Completed || Status == ServiceOrderStatus.Cancelled` — **primeira transição do projeto que aceita mais de um status de origem** (todas as outras têm uma única precondição de status) — senão `DomainException(InvalidStatusTransition)`; muda `Status` para `Delivered`; **seta `ClosedAt = DateTime.Now`** (único método que popula esse campo — `ClosedAt` fica `null` desde `CreateServiceOrder` até aqui, em qualquer um dos dois caminhos); registra em `StatusHistory`; `SetUpdatedAt()`.

**Decisão de design discutida e fechada com o usuário antes de implementar** (ver `CLAUDE.md`): o backlog original (ticket 24) previa `Deliver()` só a partir de `Completed` — refletindo a leitura literal do PDF ("Finalizada → Entregue"), mas isso deixava toda OS `Cancelled` (reprovada pelo cliente, tickets 21/22) como um beco sem saída — nada nunca setava `ClosedAt` pra ela, mesmo o veículo do cliente continuando fisicamente na oficina até ele vir buscar (mesma situação física de uma OS `Completed` esperando entrega, só que sem conserto no meio). Duas opções foram avaliadas com o usuário:
1. Setar `ClosedAt` já dentro de `Reject()` (código já mesclado, tickets 21/22) — tratando a decisão do cliente como o próprio encerramento da OS. Mais simples, mas perde a distinção entre "decidiu não consertar" (evento de decisão, instantâneo) e "veio buscar o carro" (evento físico, pode levar dias) — sem essa distinção, não dá pra saber quanto tempo um carro reprovado fica parado na oficina depois da decisão.
2. **Escolhida**: estender `Deliver()` pra aceitar `Completed` **ou** `Cancelled` como origem, mantendo `ClosedAt` só sendo setado no momento real da entrega física do veículo — mesmo endpoint (`POST /service-orders/{id}/delivery`, rota renomeada em 2026-08-16, ver §6), mesma policy (`AttendantOnly`), só a checagem de status ficou mais larga. Trata "veículo saiu da oficina" como o evento de fechamento de verdade, independente do caminho (conserto concluído ou orçamento reprovado).

A máquina de estados documentada em `docs/backlog-proximas-tarefas.md` foi atualizada pra refletir isso: `Aguardando aprovação → Cancelada → Entregue`, além do caminho principal `Recebida → Diagnosticando → Aguardando aprovação → Em execução → Finalizada → Entregue`. **É a única transição do projeto sem uma seta 1:1 no diagrama de estados original do PDF** — decisão de design que refina o desenho do desafio, não uma leitura literal dele.

#### `UseCases/Users/CreateUser/`

`CreateUserUseCase` (interface `ICreateUserUseCase`), input `CreateUserInput(CorrelationId, Name, Email, Password, Role)`:
1. Checa e-mail único via `IUserRepository.ExistsWithEmailAsync` — se já existe, loga `LogWarning` e retorna `Output` com erro (`"User with email {Email} already exists."`), sem tocar no repositório.
2. Hasheia a senha via `IPasswordService.Hash(input.Password)`.
3. Monta o `User` via `input.MapToDomain(passwordHash)` (usando `input.Role` direto, sem lógica extra) e persiste (`AddAsync` + `UnitOfWork.CommitAsync`).
4. Se o commit falhar (`CommitAsync` retorna `false`), loga `LogError` e retorna erro (`"Error saving user with email {Email}."`).
5. Em sucesso, `output.AddResult(user.MapToDto())` — **mudou em relação à versão anterior deste documento**: hoje devolve `UserResponse` (DTO), não a entidade `User` crua.

Recebe `ILogger<CreateUserUseCase>` no construtor. Cobertura de teste: 3 cenários unitários (sucesso, e-mail duplicado, falha ao salvar) em `CreateUserUseCaseUnitTests`, usando o helper `LoggerTestBase<TCategory>` (`tests/Fiap.Workshop.UnitTests/Common/`) para verificar `ILogger.Log(...)` sem tropeçar no fato de `LogWarning`/`LogError` serem extension methods (Moq não consegue mockar/verificar extension methods diretamente — é preciso verificar o `ILogger.Log<TState>` real por trás). Mais cenários de integração (sucesso, e-mail duplicado) em `CreateUserUseCaseIntegrationTests`, batendo no SQL Server real via `DatabaseFixture`.

**Mapper (`UseCases/CreateUser/Mapper/CreateUserMapper.cs`)**
- `MapToDomain(this CreateUserInput input, string passwordHash)`: `new User(Guid.NewGuid(), input.Email, input.Name, passwordHash, input.Role, DateTime.Now, DateTime.Now)`.
- `MapToDto(this User user)`: `new UserResponse(user.Id, user.Name, user.Email, user.Role.ToString())` — usado por `CreateUserUseCase` (ver acima) e por `GetUsersMapper` (ver `UseCases/GetUsers/` abaixo).

**Bug corrigido em 2026-08-12**: até então, `MapToDomain` usava **`input.CorrelationId` como `Id` do `User`**, em vez de gerar um `Guid` novo — diferente do padrão usado em `CreateCustomer` (`Guid.NewGuid()`, ver abaixo). Isso quebrou em produção: um cliente que reenvia a mesma requisição com o mesmo `CorrelationId` (timeout, duplo clique, retry) faz a segunda tentativa colidir com a `PRIMARY KEY` da tabela `Users`, gerando um `DbUpdateException` (violação de PK) em vez do erro amigável de "e-mail já existe" — porque o conflito acontece no `Id`, não no `Email`, então `ExistsWithEmailAsync` não pega o caso antes do `INSERT`. Corrigido trocando para `Guid.NewGuid()`, alinhando com `CreateCustomer`.

#### `UseCases/Users/ChangePassword/` (novo, branch atual `feature/8-put-users`)

`ChangePasswordUseCase` (interface `IChangePasswordUseCase`), input `ChangePasswordInput(CorrelationId, UserId, CurrentPassword, NewPassword)` — desenhado como **troca self-service** (o usuário prova que é ele mesmo enviando a senha atual), não reset administrativo:
1. Busca o usuário por id — não existe → `LogWarning` + erro `"Unable to find user"`.
2. Verifica a senha atual via `IPasswordService.Verify(input.CurrentPassword, user.Password)` — inválida → `LogWarning` + erro `"Invalid current password"`, **sem persistir nada** (`Update` nunca é chamado nesse caminho).
3. Hasheia a nova senha (`IPasswordService.Hash`) e aplica via `user.ChangePassword(newPasswordHash)` (método de comportamento, ver §3 — mesma lógica de "mutar, não reconstruir" do `UpdateProfile`).
4. Persiste (`Update` + `UnitOfWork.CommitAsync`) — falha → `LogError` + erro `"Error changing password for user with id {UserId}."`.
5. Sucesso → `output.AddResult(user.MapToDto())` (`UserResponse` não expõe `Password`, seguro devolver).

**Endpoint Api** (`PATCH /api/v1/users/{id}/password`, ver §6) implementado no mesmo dia — a decisão de método HTTP: `PUT` fica descartado porque a operação **não é idempotente** (uma segunda chamada idêntica falha, já que `CurrentPassword` deixa de bater depois da primeira troca), o que viola a exigência de idempotência do `PUT` por spec; `PATCH` não exige idempotência (RFC 5789) e descreve corretamente "atualização parcial de um campo do recurso `User`" — o argumento inicial contra `PATCH` (que ele só devia carregar o valor-alvo, não uma prova/precondição) foi revisto: nada impede um `PATCH` de carregar uma precondição (paralelo a `If-Match`/ETag), e como não há efeito colateral adicional hoje (sem invalidar sessão, sem e-mail de aviso, sem log de auditoria), `POST`-como-ação ficaria over-engineered pro que o sistema faz agora.

**Revogação de token discutida e descartada por enquanto**: trocar a senha **não invalida** nenhum JWT já emitido — eles continuam válidos até expirar (`Jwt:ExpirationInMinutes`, fallback 60min). O `JwtService` (ver §5) é totalmente stateless (sem `jti`, sem tabela de sessão, sem denylist), então revogação de verdade exigiria uma mudança estrutural na autenticação inteira (ex.: `TokenVersion`/`SecurityStamp` no `User` + validação customizada no pipeline JWT) — fora do escopo desta feature, registrado como limitação conhecida (ver §9).

Cobertura: unitários (`ChangePasswordUseCaseUnitTests` — 4 cenários: sucesso, usuário não existe, senha atual inválida, falha ao salvar) e integração (`ChangePasswordUseCaseIntegrationTests` — troca via `ICreateUserUseCase` real + confere com `IPasswordService.Verify` real (BCrypt) que a senha nova bate e a antiga não bate mais; falha usuário não existe; falha senha atual incorreta). Domínio: `UserUnitTests.User_ShouldChangePassword_WhenChangePasswordIsCalled` confirma `Password` alterado, `UpdatedAt` avançado, zero eventos novos.

Cobertura: unitários (`GetServiceOrderUseCaseUnitTests` — sucesso, com asserção de que `Parts`/`Services`/`StatusHistory` vêm vazios pra uma OS recém-mockada; e não encontrado) e integração (`GetServiceOrderUseCaseIntegrationTests` — três cenários: sucesso sem filhos via `ICreateServiceOrderUseCase` real, sucesso **com** filhos, e não encontrado).

**Achado durante o teste de integração "com filhos", registrado mas não corrigido nesta branch** (fora de escopo pra `GetServiceOrder`, que só lê): tentar popular o cenário via "abrir OS pelo use case → carregar de volta → chamar `AddParts`/`AddServices`/`AddStatusHistory` no agregado já existente → `IServiceOrderRepository.Update(...)`" **não persiste os filhos novos**, silenciosamente. Causa raiz: `Repository<T>.Upsert` (ver §5), quando o agregado raiz não está rastreado pelo `ChangeTracker` (caso comum — `DbContext` novo por escopo), cai em `set.Update(model)`; esse `Update()` do EF Core percorre o grafo desconectado e marca cada entidade filha como `Added` só se a chave for o valor default — como `ServiceOrderPartModel`/`ServiceOrderServiceModel`/`ServiceOrderStatusHistoryModel` sempre chegam com um `Guid` já atribuído (construtor exige `id`, nunca um valor default), o EF marca todas como `Modified`, gera `UPDATE ... WHERE Id = @p` pra linhas que não existem, o SQL Server afeta zero linhas sem lançar exceção (nenhum concurrency token configurado), e `CommitAsync` devolve `true` porque a própria raiz teve alguma coluna escalar alterada. **Isso é exatamente o fluxo que o ticket 20 (`AddBudget`) vai precisar** ("carregar OS existente → adicionar peças/serviços → persistir") — `Repository<T>.Upsert`/`ServiceOrderRepository.Update` precisam de um ajuste (reconciliar a coleção filha por filha — marcar `Added` os novos, `Modified` os existentes, `Deleted` os removidos — em vez de um `set.Update(model)` cego num grafo desconectado) antes de `AddBudget` poder ser implementado corretamente. O teste de integração deste ticket contorna o problema montando a `ServiceOrder` inteira (raiz + filhos) **antes** do primeiro `AddAsync` (mesmo padrão do `ServiceOrderRepositoryTests.ShouldPersistChildren`, que nunca exercitou o caminho de update).

**Atualização (`feature/19-start-diagnosis`): esse gap foi parcialmente corrigido — ver `IServiceOrderRepository.UpdateAsync` em §5.** `StartDiagnosis` (abaixo) precisou exatamente desse fluxo (carregar OS → adicionar item novo a `StatusHistory` → persistir) uma etapa antes do previsto pelo backlog original. `Parts`/`Services` continuam com o gap descrito acima, pendentes pro ticket 20.

#### `UseCases/ServiceOrders/AddBudget/` (novo, branch atual `feature/20-add-budget`, ticket 20)

`AddBudgetUseCase` (interface `IAddBudgetUseCase`), input `AddBudgetInput(CorrelationId, ServiceOrderId, ChangedBy, Services: IReadOnlyCollection<AddBudgetServiceItem>, Parts: IReadOnlyCollection<AddBudgetPartItem>)` — **sem `Discount`** (ver §3, decisão revista) — `AddBudgetServiceItem(ServiceId, Quantity)`/`AddBudgetPartItem(InventoryItemId, Quantity)` são records auxiliares no mesmo arquivo do input (não boundary próprio cada um — cohesão, só usados aqui). **Primeiro use case do projeto a injetar três repositórios e orquestrar dois agregados na mesma transação** (`ServiceOrder` + `InventoryItem`, via `IServiceOrderRepository`/`IServiceRepository`/`IInventoryItemRepository`):
1. Busca a OS por id — não encontra → `LogWarning` + erro `"Unable to find service order"`.
2. Para cada peça pedida: busca o `InventoryItem` — não encontra → `LogWarning` + erro `"Unable to find inventory item"`, retorna. Se encontrar, já chama `inventoryItem.Reserve(partItem.Quantity)` (ver §3) e monta o `ServiceOrderPart` "fotografado" via `inventoryItem.MapToServiceOrderPart(serviceOrder.Id, partItem.Quantity)` (extension method no `Mapper/AddBudgetMapper.cs` da Application, ver abaixo — não é `new ServiceOrderPart(...)` inline no use case) — tudo no mesmo loop, sem um loop separado pareando duas listas por índice (jeito inicial, trocado por ser frágil).
3. Mesma coisa para cada serviço pedido, contra `IServiceRepository` — erro `"Unable to find service"` se não encontrar. Monta o `ServiceOrderService` fotografado via `service.MapToServiceOrderService(serviceOrder.Id, serviceItem.Quantity)` (mesmo mapper). **Sem `Reserve` equivalente** — `Service` não tem estoque, só `InventoryItem` tem.
4. Chama `serviceOrder.AddBudget(orderServices, parts, input.ChangedBy)` (ver §3) — pode lançar `DomainException` (`Status != Diagnosing`), sem `try/catch` local, propagando até o `DomainExceptionHandler` global. **`Reserve` (passo 2) roda antes desta checagem de status** — inofensivo, porque nada persiste até o `CommitAsync` final (passo 6); se a OS não estiver em `Diagnosing`, a reserva em memória é só descartada junto com o resto do request.
5. Se um serviço não existir (passo 3), a reserva já feita em memória nos itens de peças anteriores (passo 2) também é descartada sem nunca ter sido persistida — não há rollback explícito porque não há nada para desfazer no banco.
6. Persiste: `IServiceOrderRepository.UpdateAsync(serviceOrder, ct)` (reconcilia `Parts`/`Services`/`StatusHistory`, ver §5) + `IInventoryItemRepository.Update(item)` (sync, sem filhos, sem gap) pra cada peça reservada — todos compartilham o mesmo `AppDbContext` do escopo (repositórios `Scoped`), então um único `UnitOfWork.CommitAsync` (via `_serviceOrderRepository`) persiste tudo atomicamente.
7. Falha no commit → `LogError` + erro `"Error updating service order with id {ServiceOrderId}."` (mesma mensagem do `StartDiagnosis`).
8. Sucesso → `output.AddResult(serviceOrder.MapToDto())` — sem mapper próprio de DTO, reaproveita `CreateServiceOrderMapper.MapToDto` (já mapeia `Parts`/`Services`/`StatusHistory`, ver §4 `GetServiceOrder`).

**Por que `Reserve` não migrou pro método `ServiceOrder.AddBudget`** (pergunta levantada pelo usuário durante a review): `ServiceOrder` e `InventoryItem` são agregados diferentes, sem referência viva entre si (`ServiceOrderPart` guarda só `InventoryItemId`). `ServiceOrder.AddBudget` mutar instâncias de `InventoryItem` diretamente quebraria a fronteira entre agregados — a regra "um agregado por transação de negócio, referenciados só por Id" já seguida em todo o resto do projeto. `Reserve()` já mora corretamente em `InventoryItem` (sua própria invariante); o loop que o chama é orquestração pura, sem regra de negócio embutida, então pertence à Application (`AddBudgetUseCase`) — mesma decisão já fechada no backlog antes desta branch existir (ver `docs/backlog-proximas-tarefas.md`, "Decisões de design já fechadas" #3).

**Mapper (`UseCases/AddBudget/Mapper/AddBudgetMapper.cs`, novo)** — só instanciação, sem lógica: `MapToServiceOrderPart(this InventoryItem inventoryItem, Guid serviceOrderId, int quantity)` e `MapToServiceOrderService(this Service service, Guid serviceOrderId, int quantity)`, cada um só um `new ServiceOrderPart(...)`/`new ServiceOrderService(...)` "fotografando" os campos do catálogo. Extraído do corpo do use case a pedido do usuário — o `Handle` tinha ~30 linhas de instanciação inline que ficaram só duas chamadas de extension method.

Cobertura: unitários (domínio: `InventoryItem.Reserve` sucesso/estoque insuficiente, `ServiceOrder.AddBudget` sucesso/status inválido; use case: sucesso, OS não encontrada, peça não encontrada, serviço não encontrado, falha ao salvar) e integração (use case fim-a-fim contra SQL Server real: sucesso reservando estoque de verdade, peça não encontrada, `DomainException` por estoque insuficiente, `DomainException` por OS fora de `Diagnosing`; mais um teste em `ServiceOrderRepositoryTests` provando que `UpdateAsync` reconcilia `Parts`/`Services` — não só `StatusHistory` — corretamente).

- **(2026-08-04)** Modelos de infra criados para todos os agregados do domínio (`CustomerModel`, `VehicleModel`, `InventoryItemModel`, `ServiceModel`, `ServiceOrderModel` + `ServiceOrderPartModel`/`ServiceOrderServiceModel`/`ServiceOrderStatusHistoryModel` como filhos, com `HasMany().WithOne().OnDelete(Cascade)`), com `ModelMappers`/`DomainMappers` e configuração completa em `AppDbContext.OnModelCreating` (índices únicos em `Document/Email/Phone` do Customer, `LicensePlate`, `Code`, `Number`; FKs explícitas entre agregados sem navegação — ex. `Vehicle.CustomerId → Customers` — via `HasOne<T>().WithMany().HasForeignKey().OnDelete(Restrict)`).
- **(2026-08-07)** Migration baseline **regenerada do zero** (`20260807031339_InitialCreate`, via `dotnet ef migrations add --project src/Fiap.Workshop.Infrastructure --startup-project src/Fiap.Workshop.Api`) cobrindo todos os agregados de uma vez — a pasta `Migrations/` existe só como apoio de ferramenta (gera SQL a partir do modelo real, útil pra conferir/gerar o `db/init.sql`), não é a fonte de verdade em runtime.
- **`db/init.sql` ganhou seu primeiro `ALTER TABLE` idempotente em `feature/23-complete-service-order` (ticket 23)**: até então, todo ajuste de schema (tickets 1-22) mexia numa tabela ainda dentro do bloco `IF NOT EXISTS (... 'U') BEGIN CREATE TABLE ... END` da própria feature que a criava, então nunca precisou lidar com uma tabela **já existente** ganhando uma coluna nova depois. O ticket 23 foi o primeiro a adicionar coluna em tabela já criada por uma branch anterior (`Services`/`ServiceOrderServices`, criadas no ticket 13/17) — como o `CREATE TABLE` só roda se a tabela ainda não existe, só atualizar o `CREATE TABLE` não bastaria pra bancos já provisionados (volume docker-compose local, `IntegrationTestsDb`). Padrão adotado: `IF NOT EXISTS (SELECT * FROM sys.columns WHERE object_id = OBJECT_ID(N'Tabela') AND name = 'Coluna') BEGIN ALTER TABLE ... ADD ... END`, guardado por coluna (não por tabela), logo depois do bloco `CREATE TABLE` correspondente. Vale repetir esse padrão pra qualquer ticket futuro que adicione coluna numa tabela que já existe há mais de uma branch (ex.: os `ALTER`/campo novo do ticket 23 em si, ou o `IsActive` em update administrativo dos tickets 26-29).
- **Achado, não corrigido, em `feature/23-complete-service-order`**: tentar `dotnet ef migrations add` pra manter `Migrations/` em sincronia (como a nota acima sugere que deveria ser feito) expôs que a pasta está **desincronizada da fonte de verdade real (`db/init.sql`) desde o ticket 17** (`feature/17-create-service-order`) — a coluna `Number` foi removida do agregado `ServiceOrder` e nunca existiu em `db/init.sql` (ver §3, decisão do ticket 17), mas a migration baseline nunca foi regenerada pra refletir isso, então `dotnet ef migrations add` tentava gerar um `DropColumn(Number, ServiceOrders)` só pra "alcançar" o modelo atual. Fica registrado como pendência: se `Migrations/` precisar ser usada de verdade algum dia (ex. `dotnet ef database update` num ambiente novo), alguém vai precisar resolver esse drift primeiro (rodar `migrations add` uma vez, aceitando o `DropColumn` do `Number`, antes de conseguir aplicar migrations dali pra frente).

### Endpoints existentes

**Users** (`/api/v{version}/users`)
- `GET /` — `GetUsers` (novo, `feature/7-get-users`). Tem `.RequireAuthorization("AdminOnly")`. Sem parâmetro nenhum (nem query, nem rota, nem corpo) — o `CorrelationId` passado ao use case é gerado inline no próprio endpoint (`Guid.NewGuid()`), não vem do cliente. Sempre retorna `Results.Ok(result)` (**só declara `Produces<Output>(200)`, sem `400`**) — consistente com `GetUsersUseCase` nunca marcar `IsValid = false` (ver §4): lista vazia também é `200 OK` com resultado vazio.
- `POST /` — `CreateUser`. Tem `.RequireAuthorization("AdminOnly")` — **exige um token JWT válido com role `Admin`**. Não há `.AllowAnonymous()`. **Bootstrap resolvido em 2026-08-16** (pedido direto do usuário, fora da sequência de tickets do backlog) via seed de Admin em `db/init.sql` — ver §5 e §9 item 1. Valida com `CreateUserRequestValidator` via `.WithValidation<CreateUserRequest>()`, chama `ICreateUserUseCase`. Retorna `201 Created` (`Location` lendo `result.GetResult<UserResponse>()?.Id` — tipo certo, ver §9 item 2) com o `Output` (contendo o `UserResponse` em `Result`) ou `400 BadRequest` com o `Output` (lista de erros).
- `PUT /{userId}` — `UpdateUser` (novo, `feature/8-put-users`). Tem `.RequireAuthorization("AdminOnly")`. `userId` vem da rota (`[FromRoute] Guid`, `[Required]`); corpo é `UpdateUserRequest(CorrelationId, Name, Email, Role)`. Retorna sempre `400 BadRequest` pra qualquer falha do use case (usuário não existe **ou** e-mail já em uso) — **decisão consciente, não um descuido**: diferente do `GET /customers/{id}` (que usa `404` porque só tem um jeito de falhar), `UpdateUserUseCase` bota os dois motivos no mesmo `IsValid = false`/`ErrorMessages`, sem nenhum campo que distinga "não encontrado" de "conflito"; segui o mesmo padrão do `CreateUser`/`CreateCustomer` (sempre `400`) em vez de inspecionar o texto da mensagem de erro dentro do endpoint pra decidir o status. Se um dia isso importar, a mudança certa é o `Output` carregar um código de erro, não o endpoint interpretando string.
- `PATCH /{userId}/password` — `ChangePassword` (novo, `feature/8-put-users`). `userId` vem da rota; corpo é `ChangePasswordRequest(CorrelationId, CurrentPassword, NewPassword)`. **Único endpoint com `.RequireAuthorization()` sem policy nomeada** — todos os outros usam `AdminOnly`/`AttendantOnly`; aqui a regra não é sobre role (qualquer usuário autenticado, seja `Admin`/`Attendant`/`Mechanic`, pode trocar a própria senha), é sobre identidade. Por isso o handler também injeta `ICurrentUserService` (**primeiro consumidor real dela na camada de Api** — antes só existia registrada no DI, sem nada usando) e compara `currentUser.UserId != userId` da rota, devolvendo `403 Forbidden` (`Results.Forbid()`) se não bater — essa checagem vive só no endpoint, não no use case (`ChangePasswordUseCase` trocaria a senha de qualquer `UserId` que receber; quem impõe "só a sua própria" é a Api). Fora isso, `400 BadRequest` pra "usuário não existe"/"senha atual inválida" (mesmo raciocínio de status único do `PUT`, acima), `200 OK` em sucesso.
- `DELETE /{userId}` — `DeleteUser` (novo, `feature/9-user-delete`). Tem `.RequireAuthorization("AdminOnly")`. `userId` vem da rota (`[FromRoute] Guid`, `[Required]`); sem corpo — `CorrelationId` é gerado inline (`Guid.NewGuid()`), mesmo padrão dos `GET` sem corpo (`GetUsers`/`GetCustomer`). **Primeiro (e único até agora) endpoint a devolver `204 No Content`** em vez de `200 OK`/`Output` no caminho de sucesso — decisão tomada junto com o use case (ver §4): como `DeleteUserUseCase` trata "não encontrado" como sucesso idempotente (`IsValid = true`, sem `AddErrorMessage`), o endpoint devolve `204 No Content` tanto quando o usuário existia e foi removido quanto quando já não existia; só cai em `400 BadRequest` com o `Output` se o `CommitAsync` falhar de verdade (erro de persistência). Diferente de `PUT`/`PATCH` acima, aqui o `Output` de sucesso não tem `Result`/`Messages` pra devolver, então não faz sentido embrulhar num `200` — por isso a rota quebra o padrão "sempre `Results.Ok(result)`" usado no resto do arquivo.

### Tratamento global de erro de domínio (`Handlers/DomainExceptionHandler.cs`, novo, `feature/11-create-vehicle`)

`DomainExceptionHandler : IExceptionHandler` (contrato nativo do ASP.NET Core, não é o `ValidationFilter` de FluentValidation) — registrado via `services.AddExceptionHandler<DomainExceptionHandler>()` (`Api/IoC/DependencyInjection.cs`, antes do `AddProblemDetails()`), consumido pelo `app.UseExceptionHandler()` já existente no `Program.cs`. Qualquer `DomainException` (`Domain.Abstractions`) não capturada localmente por um use case é interceptada aqui: seta `400 BadRequest` e escreve um `Output` (`Application.Commons`) com `AddErrorMessage(ex.Message)` no corpo — mesmo formato de resposta que todo o resto da Api usa pra erro de negócio. Exceções que não são `DomainException` continuam caindo no comportamento padrão do `UseExceptionHandler()` (hoje sem handler customizado, geralmente vira `500`).

**Por que isso existe**: antes desse handler, uma `DomainException` estourando de dentro de um use case (ex.: `new Vehicle(...)` com `ModelYear < ManufactureYear`) não tinha nenhum tratamento — o cliente recebia `500 Internal Server Error` genérico em vez de um `400` de regra de negócio. Isso não tinha sido notado antes porque nenhum use case até `CreateVehicle` construía uma entidade que valida algo no construtor (`ServiceOrderPart`/`ServiceOrderService` já validavam, mas não tinham use case nenhum consumindo). Resolvido de uma vez pra todos os agregados presentes e futuros, em vez de um `try/catch` local em cada use case — decisão consciente de manter os use cases livres desse tipo de boilerplate.

Sem cobertura de teste dedicada ainda: exigiria referenciar o projeto Api nos testes unitários (hoje `Fiap.Workshop.UnitTests` não referencia `Fiap.Workshop.Api`) ou usar `Fiap.Workshop.FunctionalTests` (vazio, ver §9 item 5) — registrado como gap pequeno, não bloqueante.

## 11. Domain Events — mecânica atual (importante entender antes de adicionar handlers)

> ⚠️ Ajustada em 2026-08-08: a versão anterior descrevia um bug no `CommitAsync` que **já foi corrigido** no código atual, e referenciava `AggregateRoot<TId>`/`User.Create`, que não existem mais (ver §3).

Como funciona hoje, de ponta a ponta:

1. O construtor de `User(...)` chama `RaiseDomainEvent(new UserCreatedEvent(id))` — isso só adiciona o evento a uma `List<IDomainEvent>` **em memória**, dentro do próprio objeto `User` (`AggregateRoot._domainEvents`). Isso acontece **toda vez** que um `User` é instanciado — criação de verdade (`CreateUserUseCase`) ou reidratação a partir do banco (`DomainMappers.MapToDomain`) — não existe um caminho separado para "isso já existia" (ver §3).
2. `UserRepository.AddAsync`/`Update` movem esses eventos para dentro do `AppDbContext` (`EnqueueDomainEvents`) e limpam a lista do `User` (`EnqueueEvents`, em `Repository<T>`). **Leituras (`GetByIdAsync`/`GetByEmailAsync`) não chamam `EnqueueEvents`** — o `UserCreatedEvent` gerado ao reidratar um usuário existente é descartado junto com o objeto, nunca chega a ser enfileirado. Frágil (ver §3), mas inofensivo hoje.
3. `AppDbContext.CommitAsync` roda `SaveChangesAsync` num `try/catch` **próprio** (grava o `UserModel` no SQL Server; se falhar, loga e retorna `false` direto). **Só depois**, num `try/catch` **separado**, entrega os eventos pendentes ao `IDomainEventDispatcher.DispatchAsync` — uma falha aqui só é logada, não afeta o `bool` retornado.
4. `DomainEventDispatcher` resolve via reflection quais `IDomainEventHandler<TEvent>` estão registrados no DI e invoca `HandleAsync` em cada um, **de forma síncrona**, ainda dentro da mesma requisição/antes de responder ao cliente.

**Conclusões importantes:**
- **Eventos de domínio NÃO são persistidos em lugar nenhum.** Não existe tabela de eventos, fila ou log. É puramente um mecanismo de notificação em memória, vivo só durante aquela unit of work.
- Isso **não é Event Sourcing** (o estado não é reconstruído replayando eventos — vive direto na tabela `Users`) nem **Transactional Outbox** (não há garantia de entrega; se o processo cair entre o `SaveChangesAsync` e o `DispatchAsync`, o evento se perde silenciosamente).
- **Hoje não existe nenhum `IDomainEventHandler` registrado no DI** — o dispatch acontece mas não aciona nada. Toda a infraestrutura existe, mas está inerte.
- **O bug de "falha no dispatch derruba o resultado do commit", descrito numa versão anterior deste documento, já está corrigido**: `SaveChangesAsync` e `DispatchAsync` têm `try/catch` independentes (passo 3 acima) — não é mais um pré-requisito bloqueando a adição de handlers.
